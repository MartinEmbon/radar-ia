# Radar IA · 2026-11-20

> [!summary] En 30 segundos
> Google lanzó Gemini 4 Neon, un modelo intermedio pensado para agentes y código, y sumó Tool Retrieval a la Gemini API para no mandar todos los esquemas de herramientas en cada pedido. GitHub agregó ocho conectores MCP a Copilot y un comando de `gh` para que los agentes esperen eventos de un PR sin hacer polling. Hugging Face propone adaptar un modelo abierto al harness donde va a correr.

## Lo importante

### 1. Gemini 4 Neon: el nivel intermedio de Google, orientado a agentes y código
**Qué pasó:** Google presentó Gemini 4 Neon el 18 de noviembre, entre Hydrogen (ejecución rápida del día a día) y Carbon (los proyectos largos y difíciles). En la API cuesta 3 USD por millón de tokens de entrada, 15 de salida y 0,15 de entrada en caché, con 1 millón de tokens de contexto y niveles de razonamiento hasta xhigh. Según Google, con razonamiento alto cuesta 32% menos por tarea que Carbon, y puede orquestar subagentes Hydrogen en Antigravity. Los benchmarks son los que cita Google, sin verificación independiente.
**Por qué importa:** Es un candidato real para agentes en producción por precio y contexto. Simon Willison marca que los precios de la línea Gemini 4 son confusos (Carbon tiene precio promocional hasta el 30 de noviembre), así que conviene medir costo por tarea y no solo por token.
**Fuente:** [Google, Introducing Gemini 4 Neon](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-neon/)

### 2. Tool Retrieval en la Gemini API: cargar herramientas solo cuando se necesitan
**Qué pasó:** La Gemini API incorporó Tool Retrieval, en preview y solo en la Interactions API. Se agrega una herramienta `tool_search` y se marcan las demás con `defer_loading: true`: el modelo ve nombre y descripción, y el esquema se carga recién cuando lo pide. También se puede diferir un servidor MCP remoto entero, y hay una variante del lado cliente (`"execution": "client"`) para usar tu propio registro. Funciona con Gemini 3.6 o posterior y no tiene cargo aparte; Google recomienda medir el ahorro con tu propio tráfico.
**Por qué importa:** Es el problema de todo agente con muchas herramientas o servidores MCP: los esquemas consumen contexto y empeoran la selección. El patrón sirve para diseñar agentes con catálogos grandes.
**Fuente:** [Google, Tool Retrieval in the Gemini API](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-tool-retrieval/)

### 3. GitHub Copilot suma ocho conectores MCP verificados
**Qué pasó:** En public preview para todos los planes, Copilot conecta Box, Buildkite, Calendly, ClickUp, Mixpanel, Supabase, Webflow y Wix, que se suman a más de 25 existentes (Slack, Figma, Sentry). En Business y Enterprise un admin tiene que habilitar la política "Editor preview features" y, si la allowlist de MCP es por conector, agregar los nuevos.
**Por qué importa:** MCP se consolida como forma estándar de conectar agentes a sistemas de negocio, con catálogo y control de administrador. Buen argumento para conversaciones sobre gobernanza.
**Fuente:** [GitHub Changelog](https://github.blog/changelog/2026-11-18-connect-supabase-box-calendly-and-more-to-copilot)

### 4. `gh event listen`: esperar eventos de un PR sin polling
**Qué pasó:** Con gh v2.105.0, un comando espera eventos de un pull request (reviews enviadas, cambios de estado o de head, conflictos de merge, check suites terminadas) y los imprime como JSON. Por defecto sale tras el primer evento; hay `--count`, `--follow` y `--timeout`. Está en preview y requiere acceso a GitHub Event Streams, por lista de espera.
**Por qué importa:** Es una pieza concreta para loops de agentes: esperar un review o un CI sin consultar cada tanto. Además, varios comandos de `gh` ahora sugieren esto en vez de polling.
**Fuente:** [GitHub Changelog](https://github.blog/changelog/2026-11-18-wait-for-pull-request-events-with-github-cli)

### 5. Harness adapters: adaptar un modelo abierto a tu harness
**Qué pasó:** Hugging Face propone entrenar un adaptador LoRA con aprendizaje por refuerzo dentro del harness que se va a usar (Pi, OpenCode o Hermes Agent), con el modelo base congelado. Con Qwen3.8-27B, en Terminal-Bench 2.1 con Pi pasó de 39% a unos 55% y de 2,9K a 1,5K tokens por tarea. Publicaron adaptadores, datasets y un GGUF. Los autores admiten que cada tarea se intentó una vez, probaron un solo modelo base y en una prueba fuera de distribución (AutomationBench) los resultados quedaron dentro del ruido.
**Por qué importa:** Muestra que costo y precisión de un agente dependen tanto del harness como del modelo. Es una vía para modelos abiertos baratos, aunque requiere GPUs y armar tareas de entrenamiento.
**Fuente:** [Hugging Face](https://huggingface.co/blog/harness-adapters-at-scale)

## Para Digibee
- Tool Retrieval y los conectores MCP de Copilot apuntan a lo mismo: catálogos grandes de herramientas con carga bajo demanda y control de administrador. Material para hablar de gobernanza de MCP y de por qué un catálogo de conectores necesita políticas.
- `gh event listen` refleja el patrón de agentes orientados a eventos en lugar de polling, que es el mismo razonamiento que se usa en integración.
- Simon Willison cita el caso de ChatPRD con "token fraud": grupos que abusan de pruebas gratis para revender tokens de agentes. Es un riesgo a considerar al exponer agentes o digital workers a terceros.

## Para probar
- [Gemini API Tool Retrieval](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-tool-retrieval/): tomar un agente con muchas herramientas, marcar la mayoría con `defer_loading: true` y comparar tokens de entrada. Unos 30 a 45 minutos.
- [Conectores de Copilot](https://github.blog/changelog/2026-11-18-connect-supabase-box-calendly-and-more-to-copilot): conectar Supabase desde el Copilot CLI con `/mcp` y hacer una consulta. Unos 15 minutos.
- [harness-profiler](https://github.com/afurmanov/harness-profiler): registra llamadas de skills, agentes y herramientas en una sesión de Claude Code y su costo en tokens. Repo chico (40 estrellas); unos 20 minutos.
